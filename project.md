# Мастер-промпт для Cursor: Калькулятор смет на ремонт/стройку

Вставь этот файл в корень проекта как `.cursor/rules/project.md` (или просто держи открытым как контекст) и дай Cursor команду начать с MVP-скоупа ниже.

---

## Что мы строим

Веб-сервис (основной канал) + тонкий Telegram-бот (второй интерфейс поверх того же API), который по свободному текстовому/голосовому описанию задачи («хочу положить плитку в ванной, 4 метра») выдаёт структурированную смету: материалы, работы, сроки, последовательность этапов.

**Модель монетизации (для контекста, не для кода на старте):** lead-gen — передача заявки бригадам/прорабам за комиссию/подписку, плюс white-label версия для строительных компаний. Сам калькулятор — точка входа, а не конечный продукт.

## Жёсткое архитектурное ограничение (не нарушать)

**Ни один пользовательский запрос не должен триггерить живой веб-поиск или мультиагентный research в реальном времени.** Это правило №1. Причины: непредсказуемая стоимость на масштабе, риск блокировок при скрейпинге, задержка ответа.

Вместо этого:

- **База цен собирается офлайн**, по расписанию (cron / scheduled job, раз в сутки-неделю), отдельным процессом, не связанным с пользовательским запросом.
- **На пользовательский запрос — максимум 2 дешёвых LLM-вызова**: (1) разбор голоса/текста в структурированные параметры, (2) сборка читаемого текста сметы из уже посчитанных цифр.
- **Сам расчёт — детерминированный код, не LLM.** Формулы расхода материала на м², нормы времени на работы, последовательность этапов — обычная бизнес-логика на основе таблиц/справочников, никакой генерации чисел моделью.

## Локализация и рынки старта

**Стартовые рынки: Польша (основной) → Украина (второй язык/прайс-таблица).** Россия исключена из скоупа (санкционные ограничения на платёжный процессинг делают монетизацию там нецелесообразной на старте).

- **Польша:** валюта PLN, платежи через Stripe/PayU/Przelewy24 — работают без сложностей. Юридическая форма — JDG (доступна на общих основаниях для беженцев со статусом ochrony czasowej / PESEL UKR).
- **Украина:** второй язык интерфейса (UA) и отдельная таблица цен под украинский рынок. Платежи — отдельная интеграция позже (LiqPay/WayForPay, не Stripe).
- Рассмотреть как первый нишевый сегмент **украинскую диаспору в Польше** — двуязычный (PL/UA) продукт с самого начала, эта аудитория одновременно и потенциальные клиенты (ремонт съёмного/купленного жилья), и потенциальные lead-gen партнёры (украиноязычные бригады, работающие в Польше).

## Источники данных для офлайн-сбора цен

1. **Sekocenbud** (польский рынок) — популярная и уже готовая ценовая база для составления смет (упрощённый и детальный метод), с ценами материалов, ставками рабочей силы по регионам, публикуется поквартально, доступна в электронном виде для импорта. Это **платная квартальная подписка**, не бесплатный API — нужно закладывать её стоимость в бюджет проекта, но это дешевле и легальнее любого скрейпинга/агентного сбора. Взять как базовый источник цен для польского MVP.
2. **Украинский рынок (второй этап):** аналогичного готового источника пока не выбрано — нужно отдельное исследование (может быть Мінрегіон / ДБН-нормативы или ручная калибровка). Не блокирует MVP на Польше.
3. **Ручная калиброванная таблица розничных наценок** — поверх базовой сметной цены (Sekocenbud даёт расценки для профессиональной сметы, а не розничные цены для частника) нужен корректирующий коэффициент под конкретные магазины/розницу. Обновлять руками/раз в месяц, не автоматизировать сразу.
4. (Опционально, позже) Мультиагентный сбор цен у розничных источников — **только как отдельный офлайн-скрипт/crew-джоба**, не как часть прод-пути запроса.

## Технологический стек (согласовано)

- **Backend + frontend сайта:** Python, Flask, серверный рендеринг через Jinja2 (единое приложение, без отдельного SPA-фронтенда на старте)
- **CSS:** Tailwind CSS через standalone CLI (без Node/npm-пайплайна — один бинарник компилирует классы из `.html`/`.jinja` шаблонов в один `.css` файл). Даёт полный контроль над видом без генеричного вида Bootstrap; при этом не требует ручного CSS с нуля.
- **Telegram-бот:** тонкий клиент (aiogram/python-telegram-bot), вызывает тот же Flask backend через внутренний API-эндпоинт, не дублирует логику расчёта
- **БД:** PostgreSQL (или SQLite на самом старте MVP, миграция на Postgres перед продакшеном) — таблицы: materials, works, work_norms, regional_coefficients
- **STT:** Whisper API (или аналог) для голосовых сообщений — подключается позже, не в MVP
- **LLM:** дешёвая модель (класса Haiku/mini) для двух точек: разбор запроса → JSON, и сборка финального текста сметы
- **Офлайн-сбор цен:** отдельный сервис/cron, может использовать CrewAI/агентный подход, но выполняется по расписанию, не в реальном времени пользовательского запроса

Примечание по дизайну: когда дойдём до полноценного визуального оформления (не голый MVP-скелет), закладывать осмысленную айдентику под тему стройки/ремонта — конкретную палитру и типографику, а не дефолтный шаблонный вид (кремовый фон + terracotta-акцент, или готовый Bootstrap-стиль). Внешний вид сайта = доверие пользователя, который принимает решение на основе сметы.

## MVP-скоуп (с чего начать, не пытаться сделать всё сразу)

1. Одна категория работ для начала (например, только плитка — пол/стены санузла). Не весь ремонт целиком.
2. Одна страна для начала — **Польша**. Ручная таблица цен на 10-15 материалов + 3-5 видов работ (можно взять ориентировочные значения из открытых польских источников на старте, до покупки подписки Sekocenbud), без автообновления — просто захардкоженный JSON/таблица в БД, чтобы проверить логику расчёта. Цены в PLN.
3. Один эндпоинт: `POST /api/estimate` — принимает текст (уже расшифрованный, без STT на старте), возвращает структурированную смету (JSON).
4. Простая веб-форма/чат-интерфейс на сайте (Flask + Jinja + Tailwind), вызывающая этот эндпоинт. Интерфейс сразу делать с i18n-слоем (даже если на старте только PL) — чтобы добавление UA-локали позже было переключением языкового файла, а не переписыванием фронта.
5. Telegram-бот подключить **последним шагом**, когда API уже стабилен — он просто вызывает тот же `/api/estimate`.
6. Украинская локаль (язык интерфейса + отдельная таблица цен под UA-рынок) и платёжная интеграция — отдельная итерация после того, как польский MVP посчитал хотя бы один реальный кейс end-to-end.

Голос, автообновление цен через ФГИС ЦС, мультиагентный сбор данных, PDF-экспорт, lead-gen для бригад — всё это следующие итерации после того, как MVP посчитает одну простую смету end-to-end.

## Что НЕ делать

- Не подключать веб-поиск/агентов на путь обработки пользовательского запроса
- Не использовать LLM для арифметики расчёта смет
- Не начинать сразу с полного каталога всех видов работ — расширять после MVP
- Не строить сложную мультиагентную систему до того, как проверена базовая формула расчёта на одном кейсе

## Первая задача для Cursor

Создать структуру проекта: Flask-приложение с эндпоинтом `/api/estimate`, простую БД-схему (materials, works, work_norms — с полем currency = PLN), базовый Jinja-шаблон с Tailwind (standalone CLI, watch-режим для разработки), и один рабочий кейс — расчёт сметы на укладку плитки по площади (без LLM, чистая формула), с тестовыми данными для ванной 4 м² по ориентировочным польским ценам.
